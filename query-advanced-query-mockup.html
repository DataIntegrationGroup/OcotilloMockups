Lo-fi mockup — not functional. No backend and no language model: the “plain English” box runs a small keyword matcher over ~120 fake wells, and the builder filters the same fake data in the browser. Try the example prompts, edit conditions, drag a rectangle on the map, and switch Table / Map / Split. Open questions flagged for review:
  • One query, two editors. The sentence is parsed into builder conditions; after that the builder is the source of truth and the sentence goes stale. Is that acceptable, or should editing the builder rewrite the sentence?
  • “Above the MCL” is ambiguous — latest result, any result ever, or the median? Who picks the default, and should the parser always ask?
  • What happens to phrases the parser cannot map (“has a pump test”)? Mockup drops them with a warning. Refusing to run is safer but more annoying.
  • Scope of “Find”. Wells only, or also springs, samples, and individual observations? Returning observations changes the table (one row per result) and the map (many rows per point).
  • Results update live while editing. Fine on fake data; against the real API do we need an explicit Run and a row cap?
  • Should the CQL2 text be editable for power users, or read-only so it stays a view of the builder?
  • Where does the NLP run, and what may it see? Sending a prompt to a hosted model is fine; sending well-owner data is not.
